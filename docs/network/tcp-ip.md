# TCP/IP 与 DNS 核心

核心逻辑：深入理解数据是如何在网络中传输的，特别是 TCP 的可靠性机制。

## 知识点体系

### 1. DNS 解析过程
当你在浏览器输入 `www.google.com` 时：
1.  **浏览器缓存**：查浏览器 DNS 缓存。
2.  **系统缓存**：查 hosts 文件。
3.  **路由器/ISP 缓存**：查本地 DNS 服务器。
4.  **递归查询**：本地 DNS 服务器向根域名服务器 -> 顶级域名服务器 (.com) -> 权威域名服务器 (google.com) 依次查询。
5.  **获取 IP**：返回 IP 地址，并缓存。

### 2. TCP vs UDP
*   **TCP (传输控制协议)**：
    *   **可靠**：面向连接，有确认、重传、排序、流控机制。
    *   **慢**：握手、挥手、头部开销大。
    *   **场景**：网页、邮件、文件传输 (HTTP, FTP, SMTP)。
*   **UDP (用户数据报协议)**：
    *   **不可靠**：无连接，发出去就不管了，可能丢包、乱序。
    *   **快**：头部小，无拥塞控制。
    *   **场景**：视频会议、直播、DNS、QUIC。

### 3. TCP 三次握手 (Three-way Handshake)
**目的**：建立可靠连接，确认双方的**发送**和**接收**能力都正常，并同步初始序列号 (ISN)。

**流程图解**：
```
Client (CLOSED) -> [SYN, seq=x] -> Server (LISTEN)
Client (SYN_SENT) <- [SYN, ACK, seq=y, ack=x+1] <- Server (SYN_RCVD)
Client (ESTABLISHED) -> [ACK, ack=y+1] -> Server (ESTABLISHED)
```

1.  **第一次握手 (SYN)**：客户端发送 SYN 报文，请求建立连接。说明客户端**发送**能力正常。
2.  **第二次握手 (SYN+ACK)**：服务端收到 SYN，发送 SYN+ACK。说明服务端**接收**、**发送**能力正常。
3.  **第三次握手 (ACK)**：客户端收到，发送 ACK。服务端收到后，确认客户端**接收**能力正常。连接建立。

### 4. TCP 四次挥手 (Four-way Wave)
**目的**：断开连接。因为 TCP 是**全双工**的，发送方和接收方都需要单独关闭。

**流程图解**：
```
Client (ESTABLISHED) -> [FIN, seq=u] -> Server (ESTABLISHED)
Client (FIN_WAIT_1) <- [ACK, ack=u+1] <- Server (CLOSE_WAIT)
... Server 继续发送剩余数据 ...
Client (FIN_WAIT_2) <- [FIN, seq=v] <- Server (LAST_ACK)
Client (TIME_WAIT) -> [ACK, ack=v+1] -> Server (CLOSED)
... 等待 2MSL ...
Client (CLOSED)
```

1.  **第一次挥手 (FIN)**：客户端发 FIN，说“我没数据发了，想关”。客户端进入 `FIN_WAIT_1`。
2.  **第二次挥手 (ACK)**：服务端收到，回 ACK，说“知道了，但我可能还有数据没发完，你等等”。客户端进入 `FIN_WAIT_2`。服务端进入 `CLOSE_WAIT`。
3.  **第三次挥手 (FIN)**：服务端数据发完了，发 FIN，说“我也没数据了，关吧”。服务端进入 `LAST_ACK`。
4.  **第四次挥手 (ACK)**：客户端收到，回 ACK，说“好的，拜拜”。客户端进入 `TIME_WAIT`，等待 2MSL 后关闭。服务端收到 ACK 后直接关闭。

## 面试官怎么问

### Q1: 为什么是三次握手？两次不行吗？
**参考回答：**
**核心原因：防止失效的连接请求报文段被服务端接收，从而产生错误。**
假设只有两次握手：
1.  客户端发出的第一个 SYN 包因为网络滞留，没丢，但在连接释放后才到达服务端。
2.  服务端以为是新的连接，于是发出确认包 (ACK)，建立连接。
3.  但客户端并没有发出新连接请求，所以不理睬服务端的确认，也不发数据。
4.  服务端一直傻等，浪费资源。
**三次握手**能让客户端在收到服务端的确认后，再次确认（第三次），如果客户端没想建连，就不会发第三次 ACK，连接就建不起来。
此外，三次握手也是为了**同步双方的初始序列号**，保证数据传输的可靠性。

### Q2: 为什么是四次挥手？
**参考回答：**
因为 TCP 是**全双工**的。
*   当客户端发 FIN 时，只代表客户端**不再发送数据**了，但还能接收数据。
*   服务端收到 FIN 后，先回一个 ACK 确认收到。但服务端可能还有数据没传完，所以不能马上发 FIN。
*   等服务端数据都传完了，才能发自己的 FIN。
*   所以 ACK 和 FIN 分成了两步，加上客户端的 FIN 和最后的 ACK，一共四步。

### Q3: 为什么客户端最后要等待 2MSL (TIME_WAIT)？
**参考回答：**
MSL (Maximum Segment Lifetime) 是报文最大生存时间。2MSL 就是两个 MSL。
**原因**：
1.  **保证最后一个 ACK 能到达服务端**。如果第四次挥手的 ACK 丢了，服务端会重传 FIN。客户端在 2MSL 内收到重传的 FIN，可以再次发送 ACK。如果不等直接关闭，服务端就永远收不到 ACK，无法正常关闭。
2.  **防止旧连接的数据包干扰新连接**。等待 2MSL 可以让本连接产生的所有报文段都从网络中消失，避免新旧连接混淆。

### Q4: 什么是 SYN Flood 攻击？怎么防范？
**参考回答：**
**原理**：攻击者伪造大量 IP 向服务端发送 SYN 包（第一次握手），服务端回复 SYN+ACK 后进入 `SYN_RCVD` 状态，等待客户端回复 ACK。但因为 IP 是伪造的，永远不会有 ACK。服务端会有大量半连接占用资源，导致正常请求无法处理。
**防范**：
1.  **SYN Cookie**：服务端不直接分配资源，而是根据 SYN 计算出一个 Cookie 值作为序列号回复。只有收到客户端带回这个 Cookie 的 ACK 时，才分配资源。
2.  减少 SYN 超时时间。
3.  增加最大半连接数。
