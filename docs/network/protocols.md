# HTTPS 与协议演进

核心逻辑：网络协议的升级主要围绕着“安全”和“性能”两个核心目标。

## 知识点体系

### 1. HTTP vs HTTPS
*   **HTTP**: 明文传输，端口 80，不安全（易被窃听、篡改、冒充）。
*   **HTTPS**: HTTP + **SSL/TLS**。加密传输，端口 443，安全。
    *   **内容加密**：混合加密（非对称加密交换密钥，对称加密传输数据）。
    *   **身份验证**：数字证书。
    *   **数据完整性**：摘要算法。

### 2. TLS/SSL 握手过程 (TLS 1.2)
1.  **Client Hello**: 客户端发送支持的加密套件、随机数 `Client Random`。
2.  **Server Hello**: 服务端确认加密套件，发送数字证书、随机数 `Server Random`。
3.  **验证证书**: 客户端验证证书合法性（CA 签名、有效期等）。取出公钥。
4.  **预主密钥**: 客户端生成 `Pre-master Secret`，用**公钥加密**发送给服务端。
5.  **生成会话密钥**: 双方利用 `Client Random` + `Server Random` + `Pre-master Secret` 生成最终的**对称密钥**。
6.  **加密通信**: 之后的数据传输都用这个对称密钥进行加密。

### 3. HTTP 版本演进

#### HTTP/1.0
*   **短连接**：每次请求都建立新的 TCP 连接，用完即断。性能差。

#### HTTP/1.1 (主流)
*   **长连接 (Keep-Alive)**：默认开启。复用 TCP 连接，减少握手开销。
*   **管道化 (Pipelining)**：允许同时发送多个请求，但必须按顺序接收响应。
*   **队头阻塞 (Head-of-line Blocking)**：如果第一个请求处理慢，后面的请求都得等，即使它们已经处理好了。

#### HTTP/2.0 (变革)
*   **二进制分帧**：将报文解析为二进制帧 (Frame)，更高效。
*   **多路复用 (Multiplexing)**：解决了 HTTP 层的队头阻塞。多个请求可以在同一个 TCP 连接中乱序发送和接收，通过 Stream ID 组装。
*   **头部压缩 (HPACK)**：维护头部表，只发送差异数据，减少体积。
*   **服务端推送 (Server Push)**：服务端可以主动推送资源（如 HTML 请求后主动推 CSS）。

#### HTTP/3.0 (未来)
*   **痛点**：HTTP/2 虽然解决了 HTTP 层阻塞，但 TCP 层一旦丢包，整个连接的所有流都要等待重传 (TCP 队头阻塞)。
*   **QUIC 协议**：基于 **UDP**。
    *   **0-RTT 建连**：极快的连接建立。
    *   **无队头阻塞**：流之间相互独立，一个流丢包不影响其他流。
    *   **连接迁移**：切换网络（WiFi 切 4G）时，连接不断（基于 Connection ID 而不是 IP）。

## 面试官怎么问

### Q1: HTTPS 是绝对安全的吗？中间人攻击 (MITM) 怎么防范？
**参考回答：**
HTTPS 并非绝对安全，但能防范大部分攻击。
**中间人攻击**通常发生在证书验证阶段。如果攻击者拦截了请求，伪装成服务端发给客户端一个伪造的证书。
**防范机制**：
核心在于**数字证书体系 (PKI)**。客户端会内置受信任的根证书列表 (CA)。
1.  浏览器验证证书是否由受信任的 CA 签发。
2.  验证证书是否过期、域名是否匹配。
3.  如果证书无效，浏览器会发出红色警告，阻止用户继续访问。
*注意：如果用户手动信任了黑客的伪造证书（如抓包工具的证书），那么 HTTPS 也可以被解密。*

### Q2: HTTP/2 的多路复用和 HTTP/1.1 的 Keep-Alive 有什么区别？
**参考回答：**
*   **Keep-Alive (1.1)**：虽然复用了 TCP 连接，但请求必须**串行**处理（排队）。请求 A 回来之前，请求 B 不能发（或者发了也得等 A 先回来），存在队头阻塞。
*   **多路复用 (2.0)**：请求和响应被切分成小的**帧**，打上 Stream ID 标签。它们可以在同一个 TCP 连接中**并行**、**乱序**传输，互不干扰。

### Q3: 为什么 HTTP/3 要改用 UDP？
**参考回答：**
因为 TCP 协议的底层机制导致了无法避免的**队头阻塞**。
TCP 是可靠传输，要求数据按序到达。如果一个 TCP 包丢失，内核会等待重传，后续收到的包即使是完整的也不能交给应用层。
HTTP/2 虽然在应用层把请求分开了，但它们共用一个 TCP 连接。一旦 TCP 丢包，所有 HTTP 请求都会被阻塞。
HTTP/3 基于 UDP (QUIC)，在应用层实现了可靠传输和流控，每个流是独立的，丢包只影响当前流，彻底解决了队头阻塞问题。
