# 浏览器缓存机制

## 为什么要缓存？

网络请求是页面加载最慢的环节之一。缓存的目的是：对于**没有变化的资源**（JS、CSS、图片等），让浏览器直接使用本地保存的副本，跳过网络请求，提升加载速度，减少服务器压力。

---

## 缓存的整体流程

当浏览器发起资源请求时，会按以下顺序决策：

```
浏览器发起请求
      │
      ▼
  是否有缓存？
  ├── 没有 ──────────────────────────→ 直接请求服务器，返回资源 + 缓存策略头
  │
  └── 有缓存
         │
         ▼
    强缓存是否有效？（检查 Expires / Cache-Control）
    ├── 有效（未过期）──────────────→ 直接用缓存，不发请求（200 from cache）
    │
    └── 无效（已过期）
              │
              ▼
         协商缓存：带条件请求服务器
         （If-None-Match / If-Modified-Since）
         ├── 服务器说"没变" ────────→ 返回 304 Not Modified，浏览器用本地缓存
         └── 服务器说"变了" ────────→ 返回 200 + 新资源
```

---

## 一、强缓存

强缓存的意思是：浏览器在缓存**未过期**前，**直接使用本地缓存，不向服务器发送任何请求**。

在 Chrome DevTools 的 Network 面板中，强缓存命中时显示：
- `200 (from disk cache)` — 从磁盘缓存读取
- `200 (from memory cache)` — 从内存缓存读取（通常是当前会话内的 JS/图片）

### 控制字段：`Cache-Control`（优先）

HTTP/1.1 引入，**优先级高于 `Expires`**，是现代 Web 的标准做法。

服务器在响应头中设置：

```http
HTTP/1.1 200 OK
Cache-Control: max-age=31536000
```

常用指令：

| 指令 | 含义 |
| --- | --- |
| `max-age=<秒数>` | 资源在 N 秒内有效，相对时间 |
| `no-cache` | **不是不缓存**，而是每次使用前必须向服务器验证（走协商缓存） |
| `no-store` | 完全不缓存，每次都从服务器获取 |
| `public` | 可以被任何中间节点（CDN、代理）缓存 |
| `private` | 只能被浏览器缓存，不允许 CDN 缓存（如登录后的个人页面） |
| `must-revalidate` | 缓存过期后必须向服务器验证，不允许使用过期缓存 |
| `immutable` | 资源内容永不改变，即使刷新也不发请求（配合内容哈希文件名使用）|

### 控制字段：`Expires`（旧，了解即可）

HTTP/1.0 的产物，直接指定一个**绝对过期时间**：

```http
Expires: Wed, 21 Oct 2026 07:28:00 GMT
```

缺点：依赖客户端时钟，如果用户系统时间不准，会导致缓存失效计算错误。现代项目已基本被 `Cache-Control: max-age` 取代。

---

## 二、协商缓存

强缓存过期后，浏览器不能直接用缓存了，但也不一定要重新下载资源。它会带着"凭证"问服务器：**"这个资源有没有更新？"**

这个"凭证"就是协商缓存的标识。

### 方式一：`ETag` / `If-None-Match`（优先，精确）

**ETag（Entity Tag）**：服务器根据资源内容生成的**唯一标识**（类似内容的哈希指纹）。

流程：
```
①  首次请求时，服务器返回：
    ETag: "abc123"

②  资源过期后，浏览器再次请求，带上：
    If-None-Match: "abc123"

③  服务器对比 ETag：
    - 相同 → 资源未变 → 返回 304（不返回内容，只有头）
    - 不同 → 资源已变 → 返回 200 + 新资源 + 新 ETag
```

### 方式二：`Last-Modified` / `If-Modified-Since`（旧，精度差）

**Last-Modified**：服务器返回资源的**最后修改时间**。

流程：
```
①  首次请求时，服务器返回：
    Last-Modified: Mon, 13 Mar 2026 12:00:00 GMT

②  资源过期后，浏览器再次请求，带上：
    If-Modified-Since: Mon, 13 Mar 2026 12:00:00 GMT

③  服务器对比时间：
    - 未变化 → 返回 304
    - 已变化 → 返回 200 + 新资源
```

### ETag vs Last-Modified 对比

| 对比项 | ETag | Last-Modified |
| --- | --- | --- |
| 精度 | 内容级别（内容改了才变）| 秒级（1 秒内多次修改无法区分）|
| 准确性 | 高（内容未变但 mtime 变了，ETag 不变）| 低（文件 touch 了但内容没变，也会返回 200）|
| 计算成本 | 服务器需要计算哈希，有额外开销 | 直接读文件时间，成本低 |
| 优先级 | 高（有 ETag 优先用 ETag）| 低（备选方案）|

## 三、缓存位置

浏览器缓存按优先级从高到低分为 4 个位置：

### 1. Service Worker Cache

- 完全可编程的缓存，由开发者用 Service Worker 脚本控制。
- 可以实现离线访问（PWA 的核心能力）。
- 存储在 Cache Storage，不受 HTTP 缓存策略限制，由代码决定缓存逻辑。

### 2. Memory Cache（内存缓存）

- 存在内存中，读取速度最快。
- **Tab 关闭后消失**。
- 通常缓存本次会话中已请求的 JS、图片等资源（`<img>` 标签引用同一图片时，第二次直接内存读取）。

### 3. Disk Cache（磁盘缓存）

- 存在硬盘中，持久化存储，关闭浏览器后依然存在。
- 容量比内存大，读取比内存慢，但比网络快得多。
- CSS、字体、较大的 JS 文件通常放在磁盘缓存。

### 4. Push Cache

- HTTP/2 的 Server Push 功能产生的缓存。
- 只在当前 HTTP/2 连接的会话中有效，连接断开即消失。
- 优先级最低，现已很少使用。

## 四、实际项目的缓存策略

### 静态资源（JS、CSS、图片）

**策略：强缓存 + 内容哈希文件名**

```http
Cache-Control: max-age=31536000, immutable
```

同时，用构建工具（Webpack/Vite）给文件名加内容哈希：

```
app.a1b2c3d4.js  ← 内容变了就换一个新哈希，URL 变了缓存自然失效
```

这样资源可以被缓存一年，而一旦代码更新，文件名改变，浏览器会请求新文件。

### HTML 文件

**策略：不强缓存，每次都验证**

```http
Cache-Control: no-cache
```

HTML 是入口文件，必须保持最新，才能加载到正确的 JS/CSS 哈希文件名。如果 HTML 被强缓存了，发布新版本时用户仍然加载旧的 HTML（里面引用旧的文件名），就看不到更新了。

### API 接口

**策略：通常不缓存**

```http
Cache-Control: no-store
```

或者对部分公共数据设置短时间缓存（如几秒到几分钟）。

## 面试官怎么问

### Q1: 强缓存和协商缓存的区别？

**参考回答：**

- **强缓存**：浏览器在缓存有效期内直接使用本地副本，**不发送网络请求**，状态码 200。控制字段：`Cache-Control: max-age`（优先）和 `Expires`（旧）。
- **协商缓存**：强缓存过期后，浏览器**发请求到服务器询问**资源是否有更新。如果未更新，服务器返回 304，浏览器继续使用本地缓存；如果更新了，服务器返回 200 + 新内容。控制字段：`ETag/If-None-Match`（优先）和 `Last-Modified/If-Modified-Since`（旧）。

两者核心区别在于**是否向服务器发请求**。

### Q2: `Cache-Control: no-cache` 和 `no-store` 有什么区别？

**参考回答：**

这是一个经典混淆点：
- `no-cache`：**不是"不缓存"**，而是"缓存了但每次使用前必须先向服务器验证"（走协商缓存）。资源仍然会被存储在本地，只是每次都需要确认是否过期。
- `no-store`：**真的不缓存**，完全不存储任何副本，每次都从服务器获取最新数据。适合极度敏感的数据（如银行交易记录）。

### Q3: 为什么强刷新（Ctrl+Shift+R）可以绕过缓存？

**参考回答：**

强刷新时，浏览器在请求头中发送：

```http
Cache-Control: no-cache
Pragma: no-cache
```

这告诉服务器（和中间代理）不要使用缓存，必须返回最新内容。普通刷新（F5）则会带上协商缓存的标识（If-None-Match 等），可能得到 304。

### Q4: 前端项目发布后，用户还是看到旧版本，是什么原因？怎么解决？

**参考回答：**

最常见的原因：**HTML 文件被强缓存了**。

解决方案：
1. 将 HTML 的缓存策略设为 `Cache-Control: no-cache`，保证用户每次都能获取最新入口文件。
2. JS、CSS 等静态资源使用**内容哈希文件名**（由 Webpack/Vite 自动生成），配合 `Cache-Control: max-age=31536000` 长期缓存。
3. 新版本发布时，JS/CSS 内容变了 → 哈希变了 → URL 变了 → 浏览器请求新文件，缓存自动失效。
