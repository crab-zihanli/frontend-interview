# 浏览器进程与线程模型

## 为什么要了解这个？

当你打开 Chrome 浏览器，后台其实启动了很多"程序"在协同工作。理解浏览器的进程/线程架构，能帮你回答诸如：
- "为什么一个 Tab 崩溃不影响其他 Tab？"
- "为什么 JS 执行会阻塞页面渲染？"
- "Web Worker 解决了什么问题？"

---

## 进程 vs 线程：基本概念

- **进程（Process）**：操作系统分配资源的最小单位。每个进程有独立的内存空间，进程之间相互隔离。
- **线程（Thread）**：CPU 调度的最小单位。一个进程内可以有多个线程，它们**共享**进程的内存空间。

**类比**：进程像一家公司，有独立的办公室（内存）；线程像公司里的员工，共用同一间办公室。

---

## Chrome 的多进程架构

Chrome 采用**多进程架构**，主要包含以下几类进程：

```
┌─────────────────────────────────────────────────────┐
│                   Browser Process                    │  ← 主控进程
│   (UI、地址栏、书签、网络请求协调、存储管理...)          │
└───────────┬──────────────┬──────────────────────────┘
            │              │
     ┌──────▼──────┐ ┌─────▼──────┐ ┌──────────────────┐
     │  Renderer   │ │  Renderer  │ │  Renderer Process │
     │  Process    │ │  Process   │ │  (每个 Tab 一个)   │
     │  (Tab A)    │ │  (Tab B)   │ └──────────────────┘
     └─────────────┘ └────────────┘

     ┌─────────────┐ ┌────────────┐
     │  GPU Process│ │  Plugin    │
     │  (GPU 渲染) │ │  Process   │
     └─────────────┘ └────────────┘

     ┌──────────────────────────────┐
     │    Network Service Process   │  ← 网络请求专用进程
     └──────────────────────────────┘
```

### 1. Browser Process（浏览器主进程）

- **唯一一个**，整个浏览器只有一个。
- 负责：地址栏、书签栏、前进/后退按钮等浏览器 UI。
- 负责：协调其他进程之间的通信。
- 负责：文件访问、网络请求的权限管理（在旧版中，新版已抽离出 Network Process）。

### 2. Renderer Process（渲染进程）

- **每个 Tab 通常对应一个**（出于安全和稳定性隔离）。
- 负责：把 HTML、CSS、JS 转换成用户能看到的页面。
- 运行在**沙箱（Sandbox）**中，无法直接访问操作系统资源，需通过 Browser Process 代理。
- 这是我们前端开发最关心的进程，内部线程结构见下文。

> 注意：同一个站点的不同 Tab 在某些条件下可能共享一个渲染进程（Site Isolation 策略相关）。

### 3. GPU Process（GPU 进程）

- 处理 GPU 相关任务，主要用于页面的**合成（Compositing）**和硬件加速绘制。
- 多进程设计是因为 GPU 驱动经常崩溃，隔离可以保护浏览器主进程。

### 4. Plugin Process（插件进程）

- 运行浏览器插件（如旧时代的 Flash），每个插件一个进程。
- 插件频繁崩溃是早期浏览器不稳定的主因，进程隔离后大幅改善体验。

### 5. Network Service Process（网络进程）

- Chrome 79+ 之后从 Browser Process 中独立出来。
- 专门负责发起网络请求、处理 HTTP 协议、管理缓存。

---

## 多进程架构的优缺点

| 特性 | 说明 |
|------|------|
| **稳定性** | 一个 Tab 崩溃（Renderer 进程挂了）不影响其他 Tab 和浏览器本身 |
| **安全性** | Renderer 进程在沙箱中运行，无法直接访问磁盘或系统 API |
| **内存开销** | 每个进程有独立内存，进程多了内存占用大（这也是 Chrome "吃内存" 的原因之一） |

---

## 渲染进程内部的线程

渲染进程是前端最核心的进程，它内部有多个线程协同工作：

```
┌────────────────────────────────────────────────────────┐
│                   Renderer Process                     │
│                                                        │
│  ┌──────────────────┐    ┌────────────────────────┐   │
│  │   Main Thread    │    │  Compositor Thread     │   │
│  │  (主线程)         │    │  (合成线程)             │   │
│  │                  │    │                        │   │
│  │ • JS 执行         │    │ • 处理滚动/动画（不经    │   │
│  │ • DOM 操作        │    │   过主线程，更流畅）     │   │
│  │ • CSS 计算        │    │                        │   │
│  │ • 布局(Layout)   │    └────────────────────────┘   │
│  │ • 绘制(Paint)    │                                  │
│  └──────────────────┘    ┌────────────────────────┐   │
│                          │  Raster Thread(s)      │   │
│  ┌──────────────────┐    │  (栅格化线程池)          │   │
│  │  Worker Threads  │    │ • 把绘制指令转成位图      │   │
│  │  (工作线程)        │    └────────────────────────┘   │
│  │ • Web Workers    │                                  │
│  │ • Service Worker │                                  │
│  └──────────────────┘                                  │
└────────────────────────────────────────────────────────┘
```

### 主线程（Main Thread）

这是**最重要**的线程，也是面试最常考的部分。

主线程负责：
1. **解析 HTML** → 构建 DOM 树
2. **解析 CSS** → 构建 CSSOM 树
3. **执行 JavaScript**
4. **计算布局（Layout）** → 确定每个元素的位置和大小
5. **绘制（Paint）** → 确定元素的绘制顺序

**核心限制：主线程同一时间只能做一件事。**

这就是为什么：
- JS 执行时间过长会**阻塞渲染**（页面卡死）
- `<script>` 标签默认会阻塞 HTML 解析（因为 JS 可能操作 DOM）

### 合成线程（Compositor Thread）

- 独立于主线程，不受 JS 影响。
- 负责将已绘制好的图层**合成**最终画面并上屏。
- CSS 动画如果只涉及 `transform` 和 `opacity`，可以直接在合成线程完成，**不阻塞主线程** → 这就是为什么推荐用这两个属性做动画。

---

## 知识延伸：为什么 JS 是单线程的？

JavaScript 设计之初就是单线程，原因是：JS 需要操作 DOM，如果多个线程同时操作 DOM（一个线程添加节点，另一个线程删除同一个节点），会产生难以预料的冲突。

单线程 + 事件循环（Event Loop）是 JS 处理并发的核心机制（见 `event-loop.md`）。

## 面试官怎么问

### Q1: Chrome 为什么采用多进程架构？

**参考回答：**

Chrome 早期也是单进程架构，但有三个严重问题：
1. **稳定性差**：任意一个 Tab 的插件崩溃，整个浏览器都会崩溃。
2. **安全性差**：单进程无法对各模块做权限隔离，恶意页面可以访问系统资源。
3. **性能差**：单进程无法充分利用多核 CPU。

多进程架构解决了上述问题，代价是内存占用增加，但现代硬件内存足够大，这个代价是值得的。

### Q2: 渲染进程里有哪些线程？各自负责什么？

**参考回答：**

渲染进程主要包含：
- **主线程**：解析 HTML/CSS、执行 JS、布局、绘制——所有的"主要工作"都在这里。
- **合成线程**：负责把图层合成成最终画面，可以独立于主线程运行，让滚动和某些动画更流畅。
- **栅格化线程**：把绘制指令（矢量）转成实际位图，供 GPU 使用。
- **Worker 线程**：运行 Web Worker / Service Worker，执行不操作 DOM 的后台计算任务。

### Q3: 为什么 `<script>` 标签要放在 `<body>` 底部？

**参考回答：**

浏览器解析 HTML 是从上到下的，遇到 `<script>` 标签时，主线程必须：
1. 停止解析 HTML（因为 JS 可能改变后续 DOM 结构）
2. 下载并执行脚本
3. 执行完成后，继续解析 HTML

如果 `<script>` 在 `<head>` 里，此时 `<body>` 还没解析，JS 无法访问页面元素，且用户看到白屏等待 JS 执行完毕。

放到 `<body>` 底部可以保证：DOM 已经构建完毕再执行 JS，同时减少白屏时间。

现代方案是使用 `defer` 或 `async` 属性：
- `defer`：异步下载，在 HTML 解析完成后、`DOMContentLoaded` 触发前按顺序执行。
- `async`：异步下载，下载完立即执行（不保证顺序）。

### Q4: 什么是沙箱（Sandbox）？

**参考回答：**

沙箱是浏览器的安全机制：渲染进程（运行网页代码的进程）被限制了操作系统权限，它不能直接：
- 读写文件系统
- 建立网络连接
- 访问其他进程的内存

所有需要这些能力的操作，都必须通过 IPC（进程间通信）发消息给 Browser Process，由 Browser Process 代为执行并返回结果。

这样即使某个网页包含恶意代码，也无法直接危害用户的操作系统。
